I'll provide two solutions for updating a shared counter with concurrency safety - one using locks (pessimistic) and one using CAS operations (optimistic).

## Solution 1: Using Mutex Lock (Pessimistic)

```python
import threading
import time
import random

class SharedCounter:
    def __init__(self, initial_value=0):
        self.value = initial_value
        self.lock = threading.Lock()
    
    def increment(self, amount=1):
        """Thread-safe increment operation using a mutex lock"""
        with self.lock:
            self.value += amount
            return self.value
    
    def get_value(self):
        """Thread-safe read operation"""
        with self.lock:
            return self.value

# Example usage with worker threads
def worker(counter, iterations, worker_id):
    for i in range(iterations):
        # Simulate some work
        time.sleep(random.uniform(0, 0.001))
        # Increment the counter
        counter.increment()
    print(f"Worker {worker_id} completed")

# Test the implementation
counter = SharedCounter()
threads = []

# Create 5 workers, each doing 1000 increments
for i in range(5):
    t = threading.Thread(target=worker, args=(counter, 1000, i))
    threads.append(t)
    t.start()

# Wait for all threads to complete
for t in threads:
    t.join()

print(f"Final counter value: {counter.get_value()}")
print(f"Expected value: {5 * 1000}")
```

## Solution 2: Using Atomic Operations with CAS (Optimistic)

```python
import threading
import time
import random

class AtomicCounter:
    def __init__(self, initial_value=0):
        self.value = initial_value
        self.lock = threading.Lock()  # We'll use a lock for the CAS operation itself
        
    def compare_and_swap(self, expected, new_value):
        """Atomic compare-and-swap operation"""
        with self.lock:
            if self.value == expected:
                self.value = new_value
                return True
            return False
    
    def increment(self, amount=1):
        """Lock-free increment using CAS with retry"""
        while True:
            current = self.get_value()
            new_value = current + amount
            if self.compare_and_swap(current, new_value):
                return new_value
            # If CAS fails, someone else modified the value, retry
    
    def get_value(self):
        with self.lock:
            return self.value

# Alternative: Using Python's built-in atomic operations
```

## Solution 3: Using Python's threading.Lock with RLock for Reentrancy

```python
import threading
import time
import random
from collections import defaultdict

class ThreadSafeCounter:
    def __init__(self, initial_value=0):
        self._value = initial_value
        self._lock = threading.RLock()  # Reentrant lock allows same thread to acquire multiple times
        
    def increment(self, amount=1):
        with self._lock:
            self._value += amount
            return self._value
    
    def decrement(self, amount=1):
        with self._lock:
            self._value -= amount
            return self._value
    
    def get_value(self):
        with self._lock:
            return self._value
    
    def reset(self, new_value=0):
        with self._lock:
            self._value = new_value
            return self._value

# Example with complex update scenario
def complex_worker(counter, worker_id):
    """Demonstrates complex multi-step update operations"""
    for _ in range(500):
        # Simulate multiple operations that need to be atomic together
        with counter._lock:  # Direct lock access for atomic multi-step operations
            # Check conditions
            if counter.get_value() < 0:
                counter.reset(0)
            # Perform multiple updates atomically
            current = counter.get_value()
            # Some complex business logic
            increment = random.randint(1, 5)
            current += increment
            
            # Simulate a validate-then-update pattern
            counter._value = current  # We have the lock, so this is atomic
        time.sleep(random.uniform(0, 0.0005))
    
    print(f"Worker {worker_id} completed")

# Test with complex operations
counter = ThreadSafeCounter()
threads = []

for i in range(3):
    t = threading.Thread(target=complex_worker, args=(counter, i))
    threads.append(t)
    t.start()

for t in threads:
    t.join()

```

## Key Concepts:

1. **Mutex Lock (Pessimistic)**:
   - Acquires a lock before every operation
   - Blocks other threads until the operation completes
   - Guarantees mutual exclusion
   - Simple to reason about but can have contention issues

2. **Compare-and-Swap (CAS - Optimistic)**:
   - Tries to update assuming no conflict
   - Checks if value has changed before updating
   - Retries if conflict detected
   - Better for high-contention scenarios
   - No blocking, but may have wasted work on conflicts

3. **Python's GIL Considerations**:
   - Python's GIL makes simple operations (like `value += 1`) atomic
   - But for complex multi-step updates, explicit locking is needed
   - Use `threading.Lock` for basic mutual exclusion
   - Use `threading.RLock` if same thread might need to re-acquire

## Best Practices:
- Always use context managers (`with lock:`) for proper lock release
- Keep critical sections as short as possible
- Document thread-safety guarantees
- Test thoroughly with concurrent access
- Consider using `queue.Queue` for producer-consumer patterns

Both solutions ensure no update is lost, but they use different strategies - locking blocks and waits, while CAS retries and optimistically assumes success.
